# 讲义-项目颗粒度重构设计

## 问题

用户反馈：全课程（L01-L05 讲义 + P01-P06 项目）存在四类问题，缺一不可：

1. 讲义端概念讲解缺少数学/机制细节。
2. 讲义到项目的桥接缺失：项目代码没有明确指出对应讲义哪个公式/机制。
3. 项目内部代码讲解粒度太粗：大代码块塞进多个逻辑机制，块间缺乏结果解读。
4. 术语前后不一致或引入太突兀。

诊断范围覆盖全部 9 个讲义阶段（L01-L05）和 6 个项目（P01-P06），落地方式为：先定统一的全局颗粒度标准，再按课程原有顺序逐阶段应用。

## 全局颗粒度标准

### 讲义侧：四层结构（适用于 L02-L04 的机制性内容）

对每个核心概念：

1. **直觉动机**：要解决什么问题，不给公式。
2. **机制形式化**：关键公式/伪代码，符号显式定义；如果是已有方法的变体，说明和基线的数学差异。
3. **设计原理**：为什么选这个机制而非替代方案，至少提一个被舍弃的选项及原因。
4. **代码桥接预告**：点名对应哪个 P0x 项目、哪个函数/类，公式符号与代码变量名的对应关系（不写代码本身，只做预告）。

### 讲义侧豁免范围

L01 的 roadmap/taxonomy 概览页与整个 L05（前沿 debates）保持现有论辩/立场对比风格，不强制套四层模板，只要求达到"原理性措辞"达标（每个立场/路线都要写清楚支持者的理由与反对者的理由），不要求形式化公式。

### 项目侧：桥接与代码粒度

- 每个 notebook 开头叙述 cell 必须显式重述"本节实现讲义的哪个公式/机制"（复用讲义层4的桥接内容，不是超链接了事）。
- 现有大代码块按机制边界拆分为"一个 markdown 叙述 cell 对应一个逻辑机制的代码"，块间用 1-2 句话说明这段代码做了什么、产出什么、为什么下一步需要它。
- 只调整叙述文字和代码块切分位置，不修改代码逻辑本身（遵守仓库既有约束：notebook 代码 cell 不得随意改动）。

### 术语一致性

建立一份跨讲义术语表：记录新名词首次出现的讲义页及定义，后续讲义引用同一术语必须与首次定义一致。作为大纲的附属产出，不新增独立页面（可作为内部参考文档，不进 VitePress 导航）。

### 手算例子（可选加分项，已确认清单）

在机制形式化之后、项目对应代码块之前插入同一组数字的手算演示：

1. **P01 / L02-encoding**：VAE 重参数化，给定具体的 μ、σ、ε 数值手算 z。
2. **P02 / L02-dynamics**：RSSM 单步转移，2 维隐状态 + 1 维动作的最小转移矩阵手算。
3. **L03-planning-cem-ac / P03**：CEM 一步淘汰，5 个候选动作得分手算 top-k 淘汰。

其余机制（TD-MPC 值函数、Dreamer actor-critic 更新、Transformer 注意力、扩散模型多步采样）不做手算例子。

## 补充发现（写计划阶段核实后新增）

对比 P01-P06 的 EN/ZH notebook 叙述 cell 总字符数，发现系统性不对称：

| 项目 | EN 叙述字符数 | ZH 叙述字符数 | 比例 |
|---|---|---|---|
| P01 | 11056 | 1456 | 7.6x |
| P02 | 13540 | 1238 | 10.9x |
| P03 | 15242 | 978 | 15.6x |
| P04 | 15552 | 2569 | 6.1x |
| P05 | 11171 | 2496 | 4.5x |
| P06 | 13428 | 2983 | 4.5x |

核实 P01 后确认：EN 版叙述 cell 已经完整实现了本 spec 要求的四层结构（含公式推导、变量到代码的显式映射、设计原理对比、posterior collapse 等故障模式讨论），中文版则只有几行概述。代码 cell 本身两种语言字符数接近（P01: EN 13839 / ZH 14573），说明差距只在叙述层，不在代码实现。

**结论**：项目侧的"代码堆砌、缺讲解"问题主要是 ZH 版叙述内容缺失，不是需要从零设计新内容——EN 已经把大部分层3/层4内容写好了。因此项目侧的工作调整为：**以 EN 现有叙述为蓝本翻译改写进 ZH**（术语对齐 ZH 讲义已用的表述），而不是重新创作。代码块粒度粗（Encoder+Decoder+VAE 挤一块）这一问题在两种语言中都存在，需要两边同步拆分。讲义侧（L02-encoding 等 .md 页面）EN/ZH 本身是对称的普通翻译关系，不受此发现影响，仍按原计划补层3/层4内容。

## 执行顺序

按课程原有顺序推进，每阶段闭环后进入下一阶段：

1. L01（豁免范围内做原理性措辞检查）→
2. L02-encoding + P01（含手算例子1）→
3. L02-dynamics + L02-dynamics-dreamer-series + P02（含手算例子2）→
4. L03-planning（含手算例子3）+ P03 →
5. L03-backbone-selection + P04 →
6. L03-frontier-survey（豁免公式，仅补层3原理对比）→
7. L04（诊断框架先补可计算定义，再逐 worked example 页补层3）+ P05 + P06 →
8. L05（豁免范围，仅做原理性措辞检查）

每阶段完成后运行仓库既有验证流程（`git diff --check`、`npm run docs:build`），并检查 EN/ZH 是否同步、术语表是否有新增条目未回填。
